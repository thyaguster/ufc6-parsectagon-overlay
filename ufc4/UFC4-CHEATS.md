# UFC 4 cheat integration

## Verified local port interface

PORTHEON's UFC 4 port reads `%LOCALAPPDATA%\UFC4Native\cheats.json` during its game-image link step. Its bundled `ufc4-cheats.json` defines `ufc4_stamina_left` and `ufc4_stamina_right`, but those startup selections do not meet the overlay's live-cheat requirement. The UFC 4 menu no longer writes this file. The local config remains with an empty `enabled` list.

On the local v28 prepared game image, the stamina hook pattern has exactly one match at guest offset `0x698113`. An offline call to PORTHEON's own cheat linker applied the left, right, and combined blocks with no skipped hooks. Two runtime hook variants caused fight-start guest faults at offsets `0x69811b`–`0x69811d` even when Off. Those addresses are **8–10 bytes after the hook start**, inside the 15-byte absolute jump we had installed. The game enters the instruction at byte 8 independently. PORTHEON's own hook replaces only the first 8 bytes; the runtime absolute jump overwrote a valid entry point. Both runtime variants have been removed from the production build.

The working stamina bridge follows PORTHEON's link-time eight-byte hook and adds a separate writable four-byte mask with marker `UFC4LIVE_STAMINA1`. The hook starts with mask `0` (normal stamina). The overlay scans for the marker in a writable page and changes only the mask during the fight. It does not patch running executable code or write PORTHEON's `cheats.json`. The wrapper in `port_bridge/cheats.py` calls the port's original cheat linker for its existing packs, then appends the dormant hook and data page. The original script is backed up as `scripts/cheats_portheon.py` in the local PORTHEON install.

The port also bundles an experimental damage pack for head, body, and legs of the left fighter. Its v28 adaptation had never been tested in a fight. A local live-control prototype linked its eight-byte hook and all eight head/body/leg combinations successfully, but the user confirmed that the head toggle did not stop damage. A diagnostic hook counted 88,268 calls with head protection On and **zero** calls passing the pack's first condition, `r8 == 4`; its last sampled value was `0x7ffffffffffffffc`. The pack's v28 condition is incompatible with the tested fight. The damage submenu and bridge were removed from the working build. Finding a verified v28 health path is required before adding a live no-damage control. No bundled career money or skill-point cheat was found. UFC 6's memory addresses and hooks cannot be reused in UFC 4's native port.

The public [GoldHEN CUSA14204 17.00 trainer](https://github.com/GoldHEN/GoldHEN_Cheat_Repository/blob/main/shn/CUSA14204_17.00.shn) contains the same damage-hook logic PORTHEON adapted. It is not a separate v28 implementation. A search of public trainer source found no verified v28 no-damage patch. A second read-only v28 probe tested the proposed unified-health approach after confirmed head/body hits: the generic accessor ran 634,888 times, but its expected `rax == 4` health index occurred zero times. A sampled `100.0` value belonged to an unrelated game setting. Do not turn that accessor into a damage-blocking hook without identifying the actual health write. The diagnostic wrapper is temporary; the production bridge remains stamina-only.

Further local v28 tracing identified the head value at fighter-record offset `+0x158` and a direct health store at guest `0x698ea9` (writer function starts at `0x698cb0`). A one-shot hardware write breakpoint found this site, but the game exited with `0x80000004` (single-step) after the debugger detached; do not repeat that debugger method. The writer has two branches; the current fight exercised the branch at `0x698ea5` and not the alternate at `0x698e34`. A dormant launch-time hook at both branches preserved the valid entrypoints after eight bytes and counted real decreases. With its temporary global mask On, it blocked 944 additional downward writes during a controlled head-strike test, and both sampled fighter head values stayed unchanged. The user still saw the HEAD indicator drop, but reported no stun. This is proof of the measured health store, not yet a finished no-damage cheat: the effect currently targets both fighters, the HUD behavior needs investigation, and fighter-side selection needs a verified mapping. The installed test mask was returned to Off. All experimental scripts are ignored under `ufc4/.build`.

A read-only comparison of the first fight's two active health-owner records found values `0` and `1` at `[[owner+0x488]+0x98]`, but both fields were `0` in the next fight. A second candidate at `[[owner+0x70]+0xd8]` was `0`/`1` in one fight but `4`/`3` in the next. Both candidates are invalid as player-side identifiers. Their two test wrappers launched and ran fights with masks Off; neither was enabled. The second wrapper guards unknown side values, so the current fight remains unmodified with its mask Off.

The actual fighter record linked from `[[owner+0x4a0]+0x48]` has a stable `0`/`1` field at record offset `+0x114` in the current fight and in saved snapshots from several earlier fights. With damage blocking Off, a controlled incoming-head-hit test took the side-1 head value from about `98.8` to `82.8`; side 0 moved from `100.0` to `99.4`. This identified side 1 as the user's fighter in that fight. A third temporary wrapper using this field launched and ran with mask Off. In the next fight, a side-1 block prevented 356 downward health writes; the side-1 head value stayed `100.0`, and the user reported a falling HEAD bar but no stun or KO. A repeat with a paused before/after snapshot prevented 349 more writes, while the head value still stayed `100.0`.

The repeat snapshot found a second head-related value at actor offset `+0x1074` fell from `95.1464` to `92.8553`. The health category node's `+0x30` pointer targets that value; the same damage function writes it at guest `0x698f8d`, after the primary health write. A fourth diagnostic wrapper added a guarded clamp at the preceding six-byte instruction group `0x698f87`, preserving the original entrypoint at byte 6. It launched and ran a fight with mask Off. With side 1 protected, the hook counted six blocked primary and six blocked secondary decreases, but the user still saw the HEAD bar fall with no stun or KO. The paused before/after snapshots showed both protected fields remained at `100.0`.

The health category node also points at a third head-related field through `+0x28`. In the protected fight this field was about `54.86` while the other two were `100.0`; the same damage function writes it at guest `0x699048`. The snapshots did not include its earlier value because this target lies before the actor record base, so its role in the HUD is still an inference. A fifth diagnostic wrapper guards its eight-byte `vminss`/store group at `0x699044` for the selected actor, alongside the prior two guards. Synthetic linker/disassembly checks passed, and all four original byte patterns match the local v28 image. The active fourth-wrapper mask is Off; the fifth wrapper is not installed yet. Test fight stability with the mask Off first, then check all three fields and the visible HEAD bar under side-1 protection.

The fifth wrapper launched a fight normally with its mask Off. With side-1 protection On, it blocked 87 primary health decreases, 87 secondary decreases, and 87 auxiliary decreases across the user's extended test; other-fighter writes continued. The user reported that damage blocking still worked in a rematch but they were KOed once. Thus it is still **not a complete no-damage cheat**. The mask was returned to Off. Static disassembly shows the function computes signed impact from `xmm0` at guest `0x698d4e` before the protected writes and calls `0x697d70` at `0x698f1c` before the final two stores.

A sixth ignored diagnostic wrapper tried zeroing only negative impact for the selected actor at `0x698d4e`, alongside the fifth wrapper's guards. PORTHEON refreshed its whole UFC 4 folder before the first launch, replacing `scripts/cheats.py` with its original file; that launch had no cheat bridge. The wrapper was reinstalled and confirmed in memory and the linker log on the next launch. It then caused a fight-start fault with its mask Off. The new trampoline copied `vandps xmm2,xmm3,[rip+disp32]` without relocating the RIP-relative displacement; its Off path read the wrong constant. The sixth wrapper was removed from the game, and the verified stamina-only wrapper (`SHA256 5EDCD2B0...F9550DD2`) was restored. A corrected seventh ignored wrapper relocates that displacement; its offline linker/disassembly test asserts that the relocated read reaches exactly the original constant address. It is **not installed or tested in a fight**. Confirm the restored baseline fight before any further live test. Do not present the fifth or sixth wrapper as a finished no-damage control.

The restored stamina-only wrapper passed a fight-start check. The seventh wrapper was then installed, its marker was confirmed in game memory, and its Off path ran a fight normally. With side-1 protection On, it intercepted more than 200 negative impact events and blocked the corresponding health decreases without a process fault. The user reported **no strike damage, stun, or KO** during the fight; a submission still ended play. After that test the temporary mask was returned to Off. The working behavior was copied into `port_bridge/cheats.py` and exposed as a separate live **No damage: player 1** row in the overlay, using a dedicated writable marker (`UFC4LIVE_NODAMAGE1`). In the production menu test, the row was available and showed On; the live mask changed to `2`, the hook recorded 291 blocked health and impact events, and the user observed no health loss, stun, or KO. Turning the row Off changed the live mask to `0`, and damage resumed immediately while the fight stayed stable. The mask resets on exit; the overlay does not edit `cheats.json`. The local build and hook-boundary/mask tests passed. No UFC 4 changes are being uploaded to GitHub during development.

A dormant one-shot variant of that impact hook was tested for **Next hit KO**. With a finite impact value of `-1000`, the hook fired once and disarmed but the next head strike did not KO. At `-10000`, the hook again fired once, disarmed, and the next head strike produced a stable knockout. The game reported a red-corner KO, matching the Fight Statistics screenshot. The first live test targeted actor side 0 while the player controlled the other side. A follow-up menu build read `Fighter_ControllerInputMask` at arm time to choose the opponent dynamically. Its first arm expired with zero impacts while the user waited. On the second attempt, the game exited with a guest read fault at `0x698d5a` and `rbx=1` (SacredFire log `20261120_190639.log`). Offline disassembly showed why: the new actor-side load was encoded `41 8B 5B BC`, which wrote to **EBX**, corrupting the game's RBX pointer. The correct encoding `45 8B 5B BC` writes to R11D, whose original value the hook saves and restores. The installed core and wrapper were restored to the prior stable files before the corrected build was prepared. The failed variant remains in ignored `.build/next-hit-menu-crash-20261120`.

The corrected build passes the UFC 4 hook-boundary and writable-mask tests. Arming Next Hit KO now leaves the overlay open, and its 25-second window starts when F10 closes the menu. The installed build passed a fight with the option Off, then two consecutive armed KOs in live fights without pausing or crashing. The second arm specifically retests the path that failed in the earlier build. The user also observed that a KO can sometimes require a second strike. The hook consumes its one-shot flag on the first qualifying negative impact, but `-10000` impact is not proof that the game will register a KO on that hit. Only head strikes have been verified in live tests; the hook itself does not explicitly filter by body region. Treat first-hit and non-head KO behavior as unverified.

The local save contains `PROFILE` and `EXTRADATA0` data/index pairs. A read-only header and keyword check found career-related strings in `PROFILE`, but no identified money or skill-point field. That is insufficient to edit a save safely. Career values need a controlled before/after save comparison and a backup before a write path is considered.

## Test status

- The former startup-config helper and UI were removed after the user clarified the live-cheat requirement.
- The stamina hook/link test used the installed v28 game's prepared image without writing to the game or saves.
- Both runtime hook variants failed their in-game fight-start test with the cheat Off; the safe focus-mute build restored normal fights and passed the Windows-key audio check.
- The launch-time bridge was tested offline against a synthetic image and the actual prepared UFC 4 image. The eight-byte patch preserves the instruction at byte 8, its code reads the separate writable mask, and its extra segments have read/execute and read/write flags respectively. The overlay's marker discovery and mask changes pass a synthetic writable-page test.
- The bridge and its core passed staged in-game checks: a fight starts normally, opening Cheats with both options Off leaves the fight stable, and the left, right, and combined stamina controls work immediately during a fight without a crash. The local PORTHEON startup cheat selection remains empty; the pre-reset config and safe core are backed up in the ignored build folder.
- The damage pack's head, body, and leg blocks each link on the local v28 prepared image. The live prototype preserved the instruction after the eight-byte hook and ran fights safely with the options Off. Turning On no head damage changed its writable mask but did not protect health. A diagnostic probe confirmed that the pack's `r8 == 4` gate never passed in the tested fight. The verified stamina-only wrapper and core were restored in the local game. The damage prototype and probe are retained only under ignored `ufc4/.build` files for further investigation.

## Photo Mode & Instant Replay investigation (on hold)

- **Instant Replay (pause menu):** Scanned the live `sacredfire-game.exe` guest image (`0x800000000`–`0x804000000`); UFC 4 has **no** `fe_enable_*` pause-menu gate (`fe_enable_*` = `0`, `ReplayMenu` = `0`, `ActionReplay` = `0`), unlike UFC 6's `fe_enable_instant_replays`. UFC 4's replay properties (`Replay_IsPaused`, `Replay_Speed`, `Replay_CameraFOV`, `Replay_CameraFOV_Enabled`, `REPLAY_CAMERA_POS_X/Y/Z`, `REPLAY_CAMERA_TARGET_X/Y/Z`, `inInstantReplay`, `Global_ImmediatePlayback_*`) belong to post-KO / post-round / final replays rather than an instant-replay pause menu item.
- **Photo Mode (Freeze + Free Camera + FOV):**
  - Found the live double-buffered GPU `RenderView` blocks (`0x1001c404e0` / `0x10020404e0`: `View`, `Proj` with `FOV_Y = 21.04°` `16:9`, `ViewProj`, `CameraWorld`, `InvProj`, `InvViewProj`, `CameraPos`) referenced by Kyty's Vulkan descriptors (`0x2xxxxxxxx`).
  - Diffing `.bss` (`0x802800000`–`0x803800000`) between unpaused and paused showed no `TimeScale` (`1.0 -> 0.0`) float, only pause-menu UI flags.
  - External `WriteProcessMemory` to `0x1001c404e0` while unpaused did not move the rendered frame because the PS4 guest writes and submits to Vulkan within microseconds.
  - Capstone disassembly of `0x800000000` located `0x8011720d0` (`CamDebug` / `CameraTargetFOV`, vtable `0x8027053a0`), `0x8010e6990` (`TimeScaleDebug`, vtables `0x8026fb720` / `0x8026fb8a8`), and `0x801162ec0` (perspective `tan(fov/2)` projection builder), with `0` live vtable instances found during probe.
  - **Status:** On hold. Enabling live Photo Mode in UFC 4 requires in-process PS4 SysV ABI guest hooks in `ufc4_actions_core.dll` for both the RenderView/camera builder and simulation `dt`/freeze loop. Photo Mode and Replays remain disabled/greyed out in the UFC 4 overlay for now.
